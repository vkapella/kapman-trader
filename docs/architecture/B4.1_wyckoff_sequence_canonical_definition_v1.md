Wyckoff Sequence Canonical Definition v1 (B4.1)

Purpose
- Persist benchmark-validated, terminal-anchored Wyckoff sequences as immutable derived artifacts.
- Sequences are anchored on terminal events (SOS/SOW) and conditioned by the regime immediately prior to the terminal date.

Current module inputs
- Structural events are currently sourced from `public.daily_snapshots.events_detected`.
- The module loads the canonical event codes `SC`, `AR`, `SPRING`, `BC`, `AR_TOP`, `UT`, `SOS`, and `SOW`.
- Daily regime state is sourced from `public.daily_snapshots`, normalized to one authoritative New York trading-day row per ticker/date.
- Invalidation checks are sourced from `public.wyckoff_regime_transitions`.

Canonical sequences (v1)
1) ACCUMULATION_BREAKOUT
   - Terminal event: SOS
   - Eligibility: pre-terminal regime in ACCUMULATION or MARKDOWN
   - Supporting events (optional, ordered): SC -> AR -> SPRING

2) DISTRIBUTION_BREAKDOWN
   - Terminal event: SOW
   - Eligibility: pre-terminal regime in DISTRIBUTION or MARKUP
   - Supporting events (optional, ordered): BC -> AR_TOP -> UT

Persistence model
- Sequences are written to public.wyckoff_sequences.
- Composition is written to public.wyckoff_sequence_events.
- Terminal anchoring is mandatory; sequences do not exist without SOS/SOW.
- `events_in_sequence` JSON currently includes `sequence_type`, `terminal_event`, `prior_regime`, `entry_regime`, `post_terminal_regime`, `confidence`, `supporting_event_count`, invalidation fields, and ordered events.

Immutability and invalidation
- Sequence rows are immutable after insert.
- Invalidation is represented by invalidated=true with invalidated_reason populated.
- No deletes, no retroactive mutation.
- Terminal-day transitions are not treated as invalidations; only earlier contradictory transitions are considered invalidating.

Evidence ownership
- B4.1 does not write to wyckoff_snapshot_evidence.
- Evidence remains owned by B1/B2/B4.

Ownership and schema placement
- B4.1 ownership is logical. All sequence artifacts reside in the public schema, consistent with existing KapMan Wyckoff persistence.

Current operational assumption
- The module derives trading dates as `(time AT TIME ZONE 'America/New_York')::date`.
- If multiple `daily_snapshots` rows exist for the same ticker and NY trading day, the module prefers the latest non-null regime-bearing row; if none has a regime, it falls back to the latest row.
- Mixed historical timestamp conventions in `daily_snapshots` can still affect other consumers that read `time::date` or do not deduplicate per NY trading day.
